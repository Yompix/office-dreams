# LANTERN — прямое соединение через интернет (P2P): заметка к следующему шагу

Статус: **не сделано** (вне рамок 1.8). В 1.8 есть только прямое соединение в одной домашней сети (`scripts/join/lan_direct.gd`).

## Что есть сейчас
- Игра → мост друга (`relay_join.gd`) → WebSocket → relay (Railway) → WebSocket → мост хозяина (`relay_host.gd`) → сервер/мир.
- Задержка, которую добавляют сами мосты и relay, на localhost: p50 ≈ 1 мс (`tests/latency.sh`). Остальное — два плеча интернета
  «игрок ↔ регион Railway» (видно в приложении: «Связь с сервером LANTERN: N мс», в отчётах — регион из `/lantern/healthz`).
- 1.8: если хозяин и друг за одним роутером — потоки идут напрямую по LAN, relay нужен только для комнаты, списка игроков и чата.

## Чего хотим
Игроки в разных сетях соединяются напрямую (UDP hole punching), relay остаётся сигнальным сервером и запасным путём.
Ожидаемый выигрыш: задержка = прямой путь между игроками вместо суммы двух плеч до relay. Для двух друзей из одного города
при relay в США/Западной Европе это минус 60–200 мс; если relay уже рядом (регион EU) — минус 10–40 мс. Трафик relay падает в разы.

## Что потребуется (при нашем устройстве мостов)
1. **Свой надёжный транспорт поверх UDP.** Сейчас TCP-поток Java едет в WebSocket (TCP) и переживает обрывы за счёт `RelStream`
   (ack + досылка). Поверх UDP нужен порядок, повторы, управление окном и перегрузкой: мини-KCP/«RakNet-lite» на GDScript
   или GDExtension с готовой библиотекой (KCP, ENet из Godot — `ENetConnection` умеет работать с уже «пробитым» сокетом).
   Датаграммы Bedrock (RakNet) можно пересылать как есть — им надёжность не нужна.
2. **Сигнализация через relay**: обмен кандидатами (локальные адреса, отражённый адрес), одноразовый ключ комнаты — как
   `lan`-сообщения 1.8, но с адресами. Адрес игрока при этом узнаёт второй игрок — это надо явно показать и дать выключить
   («Прямое соединение: быстрее, но друг узнает ваш IP»); для открытых игр «Все в LANTERN» — по умолчанию выключено.
3. **Свой STUN** (UDP-порт на relay): Railway даёт только HTTP/WebSocket и TCP-прокси — UDP-сервиса нет. Нужен отдельный
   маленький UDP-сервер (VPS/Fly.io) или публичные STUN-серверы (зависимость от третьих лиц).
4. **Пробивание NAT**: одновременные UDP-пакеты с обеих сторон, 2–3 с попыток; не вышло (симметричный NAT, CGNAT мобильных
   операторов, корпоративные сети) — тихо остаёмся на relay. Реалистичная доля успеха: 60–75 % пар на домашнем Wi-Fi,
   заметно ниже на мобильном интернете.
5. **Переключение без разрыва игры**: поток начинается через relay, после успешного пробивания переезжает на прямой путь
   и обратно при потере (у `RelStream` уже есть счётчики байт и досылка — их можно использовать для «переезда»).
6. **Шифрование**: прямой UDP идёт мимо TLS relay → нужен ключ на поток (из сигнализации) и AEAD поверх датаграмм
   (в Godot есть `AESContext`/`Crypto`; проще — DTLS из `PacketPeerDTLS`, он уже в движке).
7. **Android**: фоновой службе нужен UDP-сокет и keep-alive раз в 15–20 с, иначе NAT закроет отображение; проверить
   Doze/энергосбережение у Xiaomi/Huawei.

## Риски
- Раскрытие IP-адресов игроков друг другу (сейчас их знает только relay). Нужны согласие и настройка.
- Сложность и объём тестов: свой транспорт — главный источник будущих ошибок («зависло», «отстаёт»).
- Операторские NAT: часть пар не соединится никогда — запасной путь через relay обязателен навсегда.
- Брандмауэр Windows спросит разрешение для LANTERN при первом UDP-приёме.

## Предлагаемый порядок
1. Сначала дешёвое: перенести relay в регион ближе к игрокам (EU) — по замерам пинга из отчётов 1.8.
2. STUN + пробивание только для Bedrock (датаграммы как есть, без своего транспорта) — половина пользы за четверть работы.
3. Надёжный транспорт (ENet/KCP) для Java TCP, переключение «relay ↔ напрямую» без разрыва.
